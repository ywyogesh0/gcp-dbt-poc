# gcp-dbt-poc
POC for submitting DBT job on GCP big query using different execution/orchestration options


**Note**: **Dataplex Universal Catalog was renamed Knowledge Catalog in May 2026**. 

Knowledge Catalog now provides the catalog, governance, context graph and lineage experience. For BigQuery, lineage can be captured automatically when the Data Lineage API is enabled, including lineage generated by SQL operations such as `CREATE TABLE`, `INSERT` and `MERGE`. ([Google Cloud Documentation][1])

POC Design:

```text
                    ┌──────────────────────┐
                    │ BigQuery TABLE_A     │
                    │ Raw / Source         │
                    └──────────┬───────────┘
                               │
                               │ dbt ref()
                               ▼
                    ┌──────────────────────┐
                    │ dbt model            │
                    │ transform_table_b.sql│
                    └──────────┬───────────┘
                               │
                               │ dbt run
                               ▼
                    ┌──────────────────────┐
                    │ BigQuery TABLE_B     │
                    │ Curated / Target     │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │ Knowledge Catalog    │
                    │ A → model → B        │
                    │ Lineage              │
                    └──────────────────────┘


Execution alternatives:

 Composer ───────┐
 Cloud Run ──────┤
 Dataflow ───────┤
 Cloud Build ────┼──► dbt Core ─► BigQuery
 Cloud Function ─┤
 Dataproc ───────┘

                    +
                    │
                    ▼
            Agentic AI / Gemini
                    │
          ┌─────────┼────────────┐
          ▼         ▼            ▼
       Run dbt   Validate     Analyse failure
                  data        + lineage
```

# 1. Build the common BigQuery + dbt foundation

Every orchestration option will use the same project.

Assume:

```text
GCP project:
sturdy-practice-245323

BigQuery dataset:
dbt_poc

Source:
sturdy-practice-245323.dbt_poc.table_a

Target:
sturdy-practice-245323.dbt_poc.table_b
```

Create `table_a`:

```sql
CREATE OR REPLACE TABLE `sturdy-practice-245323.dbt_poc.table_a`
(
    customer_id INT64,
    customer_name STRING,
    transaction_amount NUMERIC,
    transaction_timestamp TIMESTAMP
);
```

Load a little sample data:

```sql
INSERT INTO `sturdy-practice-245323.dbt_poc.table_a`
VALUES
(1, 'Yogesh', 100.00, CURRENT_TIMESTAMP()),
(2, 'John',   250.00, CURRENT_TIMESTAMP()),
(3, 'Sarah',   75.50, CURRENT_TIMESTAMP());
```

Your transformation requirement could be:

```text
TABLE_A
   ↓
Filter/transform
   ↓
TABLE_B

Example transformation:
- uppercase customer name
- calculate VAT
- calculate final amount
- add processing timestamp
```

# 2. Create dbt project

Install:

```bash
pip install dbt-bigquery
```

Initialize:

```bash
dbt init dbt_bigquery_poc
```

Project structure:

```text
dbt_bigquery_poc/
│
├── dbt_project.yml
│
├── profiles.yml
│
├── models/
│   ├── sources.yml
│   ├── schema.yml
│   └── transform_table_b.sql
│
├── tests/
├── macros/
└── requirements.txt
```

Your source definition:

```yaml
version: 2

sources:
  - name: source
    database: sturdy-practice-245323
    schema: dbt_poc

    tables:
      - name: table_a
```

Now:

```sql
-- models/transform_table_b.sql

{{ config(
    materialized='table',
    alias='table_b'
) }}

SELECT
    customer_id,

    UPPER(customer_name) AS customer_name,

    transaction_amount,

    transaction_amount * 0.20 AS vat_amount,

    transaction_amount * 1.20 AS final_amount,

    transaction_timestamp,

    CURRENT_TIMESTAMP() AS dbt_processed_timestamp

FROM {{ source('source', 'table_a') }}

WHERE transaction_amount > 0
```

Add tests:

```yaml
version: 2

models:
  - name: transform_table_b

    columns:
      - name: customer_id
        tests:
          - not_null
          - unique

      - name: final_amount
        tests:
          - not_null
```

Run:

```bash
dbt debug
dbt compile
dbt run --select transform_table_b
dbt test --select transform_table_b
```

You now have:

```text
BigQuery

table_a
   │
   │ dbt
   ▼
table_b
```

That is the common foundation for POCs.

# 3. Authentication

Avoid service-account JSON keys.

Create a service account:

```text
dbt-runner@sturdy-practice-245323.iam.gserviceaccount.com
```

For a POC it needs enough access to create BigQuery jobs and read/write the appropriate datasets.

Conceptually:

```text
dbt-runner
    │
    ├── BigQuery Job User
    │
    ├── BigQuery Data Viewer       → source
    │
    └── BigQuery Data Editor       → target
```

Production should narrow permissions at dataset/table level.

`profiles.yml` can use application-default credentials:

```yaml
dbt_bigquery_poc:

  target: dev

  outputs:

    dev:
      type: bigquery
      method: oauth
      project: sturdy-practice-245323
      dataset: dbt_poc
      location: europe-west2
      threads: 4
```

Inside GCP compute environments, the attached service account is preferable.

# 4. POC #1 — Cloud Composer

Option **first**.

Cloud Composer = managed Apache Airflow.

Architecture:

```text
                         Cloud Composer
                              │
                              │ DAG
                              ▼
                     ┌────────────────┐
                     │ dbt run        │
                     │ dbt test       │
                     └───────┬────────┘
                             │
                             ▼
                      BigQuery job
                             │
                 ┌───────────┴───────────┐
                 ▼                       ▼
              TABLE_A                 TABLE_B
```

There are several ways to run dbt from Composer.

For a clean enterprise pattern :

```text
Composer
    ↓
Cloud Run Job
    ↓
dbt
    ↓
BigQuery
```

rather than stuffing a large dbt installation directly inside the Airflow worker.

DAG becomes roughly:

```python
from airflow import DAG
from airflow.providers.google.cloud.operators.cloud_run import (
    CloudRunExecuteJobOperator
)
from datetime import datetime

with DAG(
    dag_id="dbt_bigquery_poc",
    start_date=datetime(2026, 1, 1),
    schedule="@daily",
    catchup=False
) as dag:

    run_dbt = CloudRunExecuteJobOperator(
        task_id="run_dbt",
        project_id="sturdy-practice-245323",
        region="europe-west2",
        job_name="dbt-bigquery-job"
    )

    run_dbt
```

Later you can make the DAG:

```text
start
  │
  ▼
check_source
  │
  ▼
run_dbt
  │
  ▼
dbt_test
  │
  ▼
validate_target
  │
  ▼
publish_metrics
  │
  ▼
end
```

For data engineering orchestration, **this is a natural Composer use case**.

# 5. POC #2 — Cloud Run

This is probably the most important execution mechanism in the POC.

Package dbt in a container.

`Dockerfile`:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

ENTRYPOINT ["dbt"]
CMD ["run"]
```

`requirements.txt`:

```text
dbt-bigquery
```

Build image:

```bash
gcloud builds submit \
  --tag europe-west2-docker.pkg.dev/sturdy-practice-245323/dbt/dbt-poc
```

Then create a **Cloud Run Job**:

```bash
gcloud run jobs create dbt-bigquery-job \
  --image=europe-west2-docker.pkg.dev/sturdy-practice-245323/dbt/dbt-poc \
  --region=europe-west2 \
  --service-account=dbt-runner@sturdy-practice-245323.iam.gserviceaccount.com
```

Execute:

```bash
gcloud run jobs execute dbt-bigquery-job \
  --region=europe-west2
```

Architecture:

```text
Trigger
   │
   ▼
Cloud Run Job
   │
   │ container
   ▼
dbt run
   │
   ▼
BigQuery
   │
   ├──── read TABLE_A
   │
   └──── write TABLE_B
```

This is arguably the cleanest place to **execute dbt Core itself**.

Cloud Run is serverless container compute, so it fits dbt's batch/container execution model very well. ([Google Cloud Documentation][2])

# 6. POC #3 — Cloud Build

Now add CI/CD.

Architecture:

```text
Git repository
      │
      │ push / PR / tag
      ▼
Cloud Build
      │
      ├── dbt deps
      ├── dbt compile
      ├── dbt test
      ├── docker build
      ├── push Artifact Registry
      └── deploy Cloud Run Job
                       │
                       ▼
                   dbt run
                       │
                       ▼
                    BigQuery
```

Example `cloudbuild.yaml`:

```yaml
steps:

  - name: python:3.12
    entrypoint: bash
    args:
      - -c
      - |
        pip install dbt-bigquery
        dbt deps
        dbt compile

  - name: gcr.io/cloud-builders/docker
    args:
      - build
      - -t
      - europe-west2-docker.pkg.dev/$PROJECT_ID/dbt/dbt-poc:$COMMIT_SHA
      - .

  - name: gcr.io/cloud-builders/docker
    args:
      - push
      - europe-west2-docker.pkg.dev/$PROJECT_ID/dbt/dbt-poc:$COMMIT_SHA

  - name: gcr.io/google.com/cloudsdktool/cloud-sdk
    entrypoint: gcloud
    args:
      - run
      - jobs
      - update
      - dbt-bigquery-job
      - --image=europe-west2-docker.pkg.dev/$PROJECT_ID/dbt/dbt-poc:$COMMIT_SHA
      - --region=europe-west2
```

The distinction is important:

```text
Cloud Build
    =
CI/CD

Cloud Run
    =
runtime

Composer
    =
workflow orchestration
```

That is the architecture I would emphasize in a design review.

# 7. POC #4 — Cloud Functions / Cloud Run functions

Google increasingly presents this capability as **Cloud Run functions**. Functions can react to events such as Pub/Sub, Cloud Storage or Eventarc. ([Google Cloud Documentation][3])

I would **not install and execute an entire dbt project inside the function**.

Instead:

```text
Event
  │
  ▼
Cloud Run Function
  │
  │ API call
  ▼
Cloud Run Job
  │
  ▼
dbt
  │
  ▼
BigQuery
```

For example:

```text
GCS file arrives
        ↓
Eventarc
        ↓
Cloud Run Function
        ↓
execute Cloud Run Job
        ↓
dbt run
        ↓
TABLE_A → TABLE_B
```

Python function conceptually:

```python
from google.cloud import run_v2

def trigger_dbt(event, context):

    client = run_v2.JobsClient()

    job_name = (
        "projects/sturdy-practice-245323/"
        "locations/europe-west2/"
        "jobs/dbt-bigquery-job"
    )

    request = run_v2.RunJobRequest(
        name=job_name
    )

    operation = client.run_job(request=request)

    return "dbt job triggered"
```

This demonstrates **event-driven dbt**.

That's useful if the requirement is:

> When source data arrives, automatically run transformation.

# 8. POC #5 — Dataflow

Here I would deliberately explain an architectural distinction.

**Dataflow should generally not exist just to run `dbt run`.**

Dataflow is Apache Beam-based data processing.

A realistic architecture is:

```text
Pub/Sub / GCS / Source
          │
          ▼
       Dataflow
          │
          │ ingest/clean
          ▼
       TABLE_A
          │
          │ completion event
          ▼
      Composer
          │
          ▼
     Cloud Run Job
          │
          ▼
         dbt
          │
          ▼
       TABLE_B
```

Or:

```text
Dataflow
   ↓
TABLE_A
   ↓
Pub/Sub
   ↓
Cloud Run Function
   ↓
Cloud Run dbt Job
   ↓
TABLE_B
```

So the POC demonstrates:

```text
Dataflow = ingestion / streaming / Beam transformation

dbt = SQL analytics transformation
```

You can technically cause a Dataflow pipeline to invoke something downstream, but designing Dataflow merely as:

```text
Dataflow
   ↓
dbt executable
```

would be an architectural smell.

A more compelling POC is:

```text
Pub/Sub transaction
       │
       ▼
 Dataflow streaming
       │
       ▼
 BigQuery TABLE_A
       │
       ▼
 dbt hourly aggregation
       │
       ▼
 BigQuery TABLE_B
```

Knowledge Catalog can also receive lineage events from Dataflow jobs through the Data Lineage API. ([Google Cloud Documentation][4])

# 9. POC #6 — Dataproc

Same principle.

Dataproc exists primarily for Spark/Hadoop workloads.

Don't introduce Spark merely to execute SQL transformations that BigQuery already handles.

For the demonstration:

```text
GCS
 │
 ▼
Dataproc Spark
 │
 │ heavy distributed processing
 ▼
TABLE_A
 │
 ▼
Composer
 │
 ▼
Cloud Run dbt
 │
 ▼
TABLE_B
```

Example:

```text
10 TB raw transaction files
          │
          ▼
      Dataproc Spark
          │
      parsing/enrichment
          │
          ▼
      BQ TABLE_A
          │
          ▼
         dbt
          │
    business modelling
          │
          ▼
      BQ TABLE_B
```

This demonstrates separation of responsibilities:

```text
Spark
   → distributed compute

BigQuery
   → analytical warehouse

dbt
   → transformation framework

Composer
   → orchestration

Cloud Run
   → dbt runtime
```

That architecture is much stronger than trying to prove that every GCP compute service can execute a `dbt` CLI command.

# 11. Knowledge Catalog lineage

Now comes the particularly good part of the demo.

Knowledge Catalog automatically discovers technical metadata for BigQuery assets such as datasets, tables, views, models and routines. ([Google Cloud Documentation][1])

Enable:

```bash
gcloud services enable \
    datalineage.googleapis.com \
    dataplex.googleapis.com
```

Run your dbt model after enabling lineage.

Because dbt ultimately submits SQL to BigQuery:

```sql
CREATE OR REPLACE TABLE table_b AS
SELECT ...
FROM table_a
```

BigQuery knows:

```text
SOURCE

sturdy-practice-245323.dbt_poc.table_a

       │
       │ BigQuery Query Job
       │
       ▼

TARGET

sturdy-practice-245323.dbt_poc.table_b
```

Knowledge Catalog can capture that relationship.

Google documents automatic BigQuery lineage for supported jobs and DDL/DML operations. ([Google Cloud Documentation][5])

Then:

```text
Google Cloud Console
      ↓
BigQuery
      ↓
dbt_poc
      ↓
table_b
      ↓
Lineage
```

You should eventually see:

```text
TABLE_A
   │
   │ BigQuery query
   ▼
TABLE_B
```

An important POC note: lineage isn't necessarily instantaneous. Google's troubleshooting guidance says that, depending on complexity and volume, lineage can take from around **30 minutes to as much as 24 hours** to appear. ([Google Cloud Documentation][6])

# 16. Give the agent tools instead of unrestricted access

This is critical.

Don't let the LLM generate arbitrary shell commands.

Expose controlled tools like:

```python
@tool
def get_source_statistics(table):
    ...

@tool
def trigger_dbt_model(model):
    ...

@tool
def get_dbt_run_status(run_id):
    ...

@tool
def execute_dbt_tests(model):
    ...

@tool
def query_bigquery(sql):
    ...

@tool
def get_table_lineage(table):
    ...

@tool
def get_data_quality_results(table):
    ...

@tool
def rollback_partition(table, partition):
    ...
```

Then the LLM decides **which safe tool to invoke**.

# 17. Multi-agent design

For a stronger demo, use specialist agents.

```text
                     SUPERVISOR AGENT
                            │
             ┌──────────────┼───────────────┐
             │              │               │
             ▼              ▼               ▼
       Metadata Agent   Pipeline Agent   Quality Agent
             │              │               │
             ▼              ▼               ▼
       Knowledge        Cloud Run/dbt    dbt tests
       Catalog                          quality scans
             │
             └──────────────┬───────────────┘
                            ▼
                       RCA Agent
                            │
                            ▼
                        User report
```

Responsibilities:

```text
Supervisor
    understands request
    ↓

Metadata Agent
    finds source/target/schema/lineage
    ↓

Pipeline Agent
    runs dbt
    ↓

Quality Agent
    validates data
    ↓

RCA Agent
    investigates failures
    ↓

Supervisor
    summarizes outcome
```

Knowledge Catalog itself is increasingly positioned as a **context layer for AI agents**: it builds a context graph of enterprise metadata designed to ground agentic applications against governed enterprise information. ([Google Cloud Documentation][10])

# 19. Even better: failure scenario

Make `table_a` suddenly contain:

```text
transaction_amount = NULL
```

Then say:

> Run today's pipeline.

Agent executes dbt.

Test fails.

Instead of simply returning:

```text
dbt test failed
```

the agent performs:

```text
Test Failure
     ↓
Retrieve run_results.json
     ↓
Query failed records
     ↓
Retrieve schema
     ↓
Retrieve lineage
     ↓
Identify upstream field
     ↓
Generate RCA
```

Response:

```text
Pipeline failed quality validation.

Failure:
final_amount NOT NULL test

Affected rows:
1,242

Root cause:
table_a.transaction_amount contains
1,242 NULL values.

Lineage:
table_a.transaction_amount
       ↓
* 1.20
       ↓
table_b.final_amount

Recommended action:
Quarantine the invalid source rows rather
than publishing table_b.

Would you like me to create the quarantine
table and rerun the model?
```

For the POC, require human approval before remediation.

That demonstrates **agent reasoning + tool calling + lineage + governance**.

# 22. This distinction will matter in your POC presentation

| Service                 | Role I'd demonstrate         | Should it execute dbt directly?      |
| ----------------------- | ---------------------------- | ------------------------------------ |
| **Cloud Composer**      | Workflow orchestration       | Possible, but preferably trigger Run |
| **Cloud Run Job**       | **Primary dbt runtime**      | **Yes**                              |
| **Cloud Build**         | CI/CD                        | Only compile/test during CI          |
| **Cloud Run Functions** | Event-driven trigger         | Prefer triggering Run                |
| **Dataflow**            | Streaming/Beam processing    | No                                   |
| **Dataproc**            | Spark/Hadoop processing      | No                                   |
| **BigQuery**            | Warehouse/SQL execution      | dbt SQL executes here                |
| **Knowledge Catalog**   | Catalog, governance, lineage | N/A                                  |
| **Gemini + ADK**        | Agentic orchestration/RCA    | Calls controlled tools               |

That separation makes the POC look like an **architectural comparison** rather than "I managed to install dbt six different ways."
